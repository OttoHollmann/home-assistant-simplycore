# SimplyCore API — Home Assistant Integration Notes

Reverse-engineered API notes for integrating SimplyCore ventilation units with Home Assistant.

**Status:** Reverse-engineered and tested against one SimplyCore unit. Other unit
versions may use different command values or support additional controls.

## 1. Connection

SimplyCore uses Socket.IO over WebSocket.

- **Endpoint:** `https://simplycore.fromargo.com/socket.io/`
- **Transport:** WebSocket
- **Engine.IO version:** 4
- **Socket.IO connection:** `EIO=4&transport=websocket`
- **Authentication:** Facility-issued token from QR code

The QR code contains a token generated by facility management. The app passes this token as `authToken` in Socket.IO event payloads.

### Authentication

The token can be obtained from any of these inputs in the Home Assistant setup form:

1. The raw facility-issued token.
2. The QR URL, in the form `https://air-link.simplycontrol.cz/<code>`. It
   redirects to `https://air-link.simplycontrol.cz/?code=<token>`; the
   integration follows that redirect and extracts the token from its query.
3. The sharing URL shown by the SimplyCore app, in the form
   `https://simplycore-link.simplycontrol.cz/code=<token>`.

The integration stores and uses the extracted token, not the supplied URL.
Only HTTPS links on the expected SimplyCore domains are accepted.

The app connects and sends a Socket.IO `connect` packet containing:

```json
{"token":"simplyAirCore"}
```

It then subscribes to the unit:

```json
[
  "unit.subscribe",
  {
    "authToken": "<QR_TOKEN>",
    "locale": "en"
  }
]
```

The actual QR token must be supplied by the user during integration setup.

## 2. Socket.IO message format

Socket.IO events are carried inside Engine.IO message packets.

Example outgoing event:

```text
42["unit.setVentilationMode",{"authToken":"<QR_TOKEN>","mode":"normal"}]
```

- `4` — Engine.IO message packet
- `2` — Socket.IO event packet
- Remaining data — JSON array containing event name and payload

Socket.IO ACK IDs may appear between the packet type and JSON payload:

```text
4210["unit.setVentilationMode",{"authToken":"<QR_TOKEN>","mode":"minimal"}]
```

Here, `10` is an ACK ID, not part of the event name.

### Connection control packets

| Packet | Meaning |
|---|---|
| `2` | Engine.IO ping |
| `3` | Engine.IO pong |
| `2probe` | WebSocket upgrade probe |
| `5` | Upgrade completed |

These are protocol-level messages, not ventilation commands.

## 3. Incoming events

### `unit_state`

The main state update event observed from the server:

```json
42["unit_state", {
  "authToken": "<QR_TOKEN>",
  "data": {
    "topic": "PUB/SC/<country>/<city>/<site>/<building>/<system>/<section>/<unit>"
  }
}]
```

The `data` object contains unit status and configuration. Relevant fields include:

| Field | Description |
|---|---|
| `powered` | Unit power state |
| `unitCondition` | Unit operating condition |
| `ventilationMode` | Current ventilation mode |
| `boostEnabled` | Whether boost functionality is available; not used as the active-boost state |
| `boosted1` | Bathroom boost state (ID `1` on the tested unit) |
| `boosted2` | Kitchen boost state (ID `2` on the tested unit) |
| `boostedFull` | Full boost state |
| `boost1Start` / `boost1End` | Start/end timestamps for bathroom boost |
| `boost1Duration` | Bathroom boost duration fallback when no end time is reported |
| `boost2Start` / `boost2End` | Start/end timestamps for kitchen boost |
| `boost2Duration` | Kitchen boost duration fallback when no end time is reported |
| `fullBoostStart` / `fullBoostEnd` | Start/end timestamps for the full-apartment boost |
| `boostFullDuration` | Full boost duration fallback when no end time is reported |
| `incomingAirHeating` | Whether incoming-air heating is active |
| `requestedTemperature` | Requested heating temperature |
| `currentFlowSupply` | Supply airflow |
| `currentFlowExhaust` | Exhaust airflow |
| `temperatureSupply` | Supply air temperature |
| `temperatureOutside` | Outside air temperature |
| `temperatureSlot1` | Temperature from configured sensor slot 1; `AIR_EXHAUST` on the tested unit |
| `co2Slot1` | CO₂ sensor slot 1 |
| `activeHeatingMode` | Active heating mode |
| `heatingModeConfiguration` | Heating mode configuration |
| `ventilationModeConfiguration` | Ventilation configuration |
| `localizedTheme` | Unit labels translated into available languages |
| `schedule` | Schedule configuration |

Example observed values:

```json
{
  "powered": true,
  "unitCondition": "on",
  "ventilationMode": "normal",
  "boostEnabled": true,
  "currentFlowSupply": 98,
  "currentFlowExhaust": 98,
  "temperatureSupply": 23.4,
  "temperatureOutside": 14.6,
  "temperatureSlot1": 23.5,
  "co2Slot1": 23,
  "requestedTemperature": 17,
  "activeHeatingMode": 1,
  "heatingModeConfiguration": {
    "mode1Temperature": 17,
    "mode2Temperature": 22,
    "mode3Temperature": 30
  }
}
```

## 4. Observed commands

All commands use the QR token in the `authToken` field.

### Subscribe to unit

```json
[
  "unit.subscribe",
  {
    "authToken": "<QR_TOKEN>",
    "locale": "en"
  }
]
```

### Set ventilation mode

```json
[
  "unit.setVentilationMode",
  {
    "authToken": "<QR_TOKEN>",
    "mode": "normal"
  }
]
```

Observed mode values:

- `normal`
- `minimal`

The Home Assistant selector displays the unit's localized theme labels for
these modes (typically "Normal" and "Vacation"). "Vacation" is still sent to
the API as the `minimal` mode value.

### Set heating mode

```json
[
  "unit.setHeatingMode",
  {
    "authToken": "<QR_TOKEN>",
    "mode": 1
  }
]
```

Observed mode values:

- `1`
- `2`
- `3`

The integration maps mode IDs `1`, `2`, and `3` to the corresponding
`mode1Temperature`, `mode2Temperature`, and `mode3Temperature` values reported
in `heatingModeConfiguration`. These three mode IDs are fixed, and the mapping
works on the tested unit. The integration selects one of the reported presets;
it does not set an arbitrary temperature or change the configured preset
temperatures. Other units may support direct temperature setting, which this
integration does not implement yet. If you have a unit that supports it and can
help with testing, contact me through the
[GitHub issue tracker](https://github.com/OttoHollmann/home-assistant-simplycore/issues);
I can investigate adding support.

### Set schedule

```json
[
  "unit.setSchedule",
  {
    "authToken": "<QR_TOKEN>",
    "schedule": {
      "enabled": true,
      "minimalVentilationEvents": [
        {
          "start": "08:00",
          "end": "17:00",
          "day": 1
        },
        {
          "start": "08:00",
          "end": "17:00",
          "day": 2
        }
      ]
    }
  }
]
```

Schedule can be enabled or disabled using the `enabled` field.

The API uses `day` value `1` for Monday and `2` for Tuesday.

#### Configure a schedule in Home Assistant

The integration's `services.yaml` defines the action form; it does not contain
fixed schedule times. Use same-day events with an end time later than the start
time; the integration does not add cross-midnight handling. After restarting
Home Assistant, open **Developer Tools
→ Actions**, select `simplycore.set_schedule`, choose the SimplyCore config
entry, and add one or more rows under **Events**. Each row has a start time,
end time, and day number. Set **Enabled** only if you also want to change the
schedule's enabled state. The action sends the entered event list to the unit,
replacing its existing `minimalVentilationEvents`.

The same action can be called from YAML:

```yaml
action: simplycore.set_schedule
data:
  entry_id: YOUR_CONFIG_ENTRY_ID
  enabled: true
  events:
    - start: "08:00"
      end: "17:00"
      day: 1
    - start: "08:00"
      end: "17:00"
      day: 2
```

In the UI, the event rows are added dynamically in the action form. An empty
`events` list clears the configured events. `entry_id` is the config entry ID
of the SimplyCore unit, not the device or an entity ID.

### Set ventilation mode configuration

```json
[
  "unit.setVentilationModeConfiguration",
  {
    "authToken": "<QR_TOKEN>",
    "configuration": {
      "normalVentilationModeTemperatureMode": 1,
      "minimalVentilationModeTemperatureMode": 1
    }
  }
]
```

Observed configuration values include `1`, `2`, and `3`.

### Start boost

```json
[
  "unit.startBoost",
  {
    "authToken": "<QR_TOKEN>",
    "boost": "full"
  }
]
```

Boost values tested on the maintainer's unit:

| Value | Description | Status |
|---|---|---|
| `1` | Bathroom boost | Works on the tested unit |
| `2` | Kitchen boost | Works on the tested unit |
| `"full"` | Full-apartment boost | Works on the tested unit |

These command mappings were reverse-engineered and may differ on other unit
versions. No boost stop command is implemented.

The full-apartment boost uses the string `"full"`, not the numeric value `3`.

## 5. Security notes

The QR token is a credential.

- Do not commit real tokens to source control.
- Redact tokens from logs and shared captures.
- Store tokens using Home Assistant's configuration entry options.
- Avoid logging complete Socket.IO payloads if they contain tokens.
